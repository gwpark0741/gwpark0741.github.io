Audyssey

A multi-track agent that splits a video's audio into one track per sound source, generates missing sounds on request, and edits each track from a text command. Work in progress; related to two KSC 2026 papers.

Fall 2026 · Capstone Design · In progress · My role: system architecture and integration, Planner/Validator, Router, integration of the in-house generation model

A five-person team project, still in progress. This page covers my parts only. I set the designs, reviewed and approved the results, and implemented them with AI coding agents (Claude Code).

Problem

Current video-to-audio models return one mixed track, so you cannot turn one sound down or fix one sound. Audyssey takes a video of up to 30 seconds, separates its audio into one track per sound source, generates sounds the video does not contain when the user asks for them, and exports the edited video and per-track audio. A silent video gets generated sound only (no speech).

Pipeline

Module What it does
Planner Reads the video and its audio (Gemini, 2 frames per second) and lists the sound sources with a type, a description, and time spans.
Validator A different model (Qwen3-VL-8B, video only, 5 frames per second) checks each source against the video and rejects sources with no evidence. Sources that pass are kept, and only the rest are planned again (at most 2 rounds).
Separator Splits one source out of the original audio with SAM Audio, ranking several candidates per sound.
Generator Makes sounds that are not in the video from the video and a text description, using an in-house generation model our team developed to raise selectivity (paper in preparation).
Reviewer Scores each separated track with the SAM Audio Judge, and each generated track with a CLAP-based margin. A track that misses the bar is retried up to 3 times.
Router Turns “bgm half as loud” into one of 8 edit commands, or asks back when the request is unclear or cannot be done.

I wrote the Planner and Validator (PRs #8, #28, #41), the Separator and Judge setup (#13, #18, #35), the Router (#38, #39), and the generation path that connects the in-house model to the pipeline (#23 to #25). I also built the server split, the Docker images, and the CI/CD.

Result

In one demo run on a 9.8-second animated fight clip, the Planner proposed 5 sources and the Validator rejected one that had no visual evidence (a body strike at 7.7 to 8.3 s). The 4 remaining sources were separated, and the Judge passed all 4 on the first try (overall 3.83 to 4.76). The whole run took about 277 seconds, including model loading. This is a single clip, not a benchmark.

Selective sound generation

A sound that is missing from the video has to be generated, and the model must make only the sound that was asked for, not extra sounds mixed in. Our team developed an in-house generation model to raise this selectivity, and it serves as the Generator in Audyssey. The research is not published yet and a paper is in preparation, so this page gives no method or numbers.

My part is bringing the model into the pipeline: connecting it to the GPU tools server, checking each generated track with a CLAP-based score, and retrying a track that misses the bar (PRs #23 to #25).

The final setup answers in 81 ms (median, local vLLM, hardware not recorded) and scored 0.846 on the held-out test set. Gemini scores higher (0.975 or more on dev) but takes about 2.5 seconds per reply. The evaluation set has 238 requests written by Claude, Codex, and Gemini, 30 of which a person checked. Conditions: 73 dev requests, 5 runs each, split by request template, 95% interval about 0.15 wide, so 0.892 and 0.906 are not statistically different. The demo uses Gemini to fill in values, so these scores are for the research setup, not for the demo.

Related papers: KSC 2026

Two KSC 2026 papers were written during this project.

Exclusion questions in audio language models (first author)

An audio language model that checks tracks must answer “is any sound other than the target audible?” correctly. Qwen2.5-Omni 7B answered “is a refrigerator audible?” correctly for an alarm clip but got “is any sound other than a refrigerator audible?” wrong, which would let a track without its target sound pass. My first-author KSC 2026 paper (accepted; listed on the About page) analyzes why models ignore the condition in these exclusion questions and fixes it with counterfactual training data.

  • Pair accuracy (both versions of a question answered correctly) rose from 5.2, 24.8, and 56.2% to 83.5, 83.9, and 84.5% for Qwen2.5-Omni 3B, 7B, and Qwen3-Omni 30B-A3B.
  • General audio understanding (MMAU test-mini) did not drop significantly.
  • Conditions: 220 human-checked separated tracks with 3 question pairs each (660 pairs), LoRA training on 4,800 examples for 150 steps, mean of 3 seeds. The paper also reports that errors on correct tracks rose (7B: 3.6 to 13.2%).

The system’s Reviewer uses the Judge and CLAP scores above, not this trained model.

Prompt rewording in text-guided audio separation (second author)

Text-guided separation models take a sentence that describes the target sound. The paper asks how much the separated audio changes when the same sound is described in different words. SAM Audio, which the Audyssey Separator uses, is one of the three models studied, together with AudioSep and CLAPSep.

  • Each of 90 target sounds was mixed into 7 inputs (alone, plus 6 mixtures with urban background sound, white or pink noise, or another sound effect) and separated with 3 phrasings of the same description, giving 1,890 outputs per model.
  • Changing only the wording changed the output waveform by 2.55% (AudioSep), 5.01% (CLAPSep), and 7.76% (SAM Audio) on average.
  • On 540 mixed inputs per model, one of the two alternative phrasings gave a higher SI-SDR than the baseline phrasing for about two thirds of inputs (65.9, 67.8, and 68.5%). The average gain of the best phrasing was 1.05, 1.19, and 3.17 dB, while the median gain was only 0.13, 0.33, and 0.07 dB.
  • For SAM Audio, changing the random seed moved the output more than changing the wording, so the seed was held fixed.

The paper suggests asking for the same sound in several phrasings and choosing among the candidates. The better candidate was found afterwards by comparing with the original sound, so choosing it on real recordings without the original, and whether listeners prefer it, still needs to be tested.

System and engineering

The GPU models (SAM Audio, the Judge, SAM 3, the generation model, CLAP) run on a GPU tools server. The app server has no GPU and calls it over HTTP with a token. The split was needed because SAM Audio’s dependencies require numpy<2, which conflicts with the rest of the app. Each tool can run as a stub, locally, or remotely, so a teammate can run only their own module with a real model. A demo run fits on one A100 80GB (peak 71,638 MiB).

  • Image deployment after changing only src/: 650 s to 7 s, measured with a warm local registry cache. On GitHub runners it took 9 to 12 minutes before.
  • Model loading: the first Judge call took 32.6 s, and later calls about 0.3 s per source (one run).
  • Tests: 455 unit tests at PR #52. Eight edit commands go through the same checks whether they come from a button, the Router, or an agent.

Limits and next steps

The demo is a single clip, no person has listened to the tracks to label them, and the generated-sound check (CLAP margin 0.0) has not been calibrated. Sources are processed one by one on a single server process, with no job queue or user accounts, so I make no claim about scale or time saved. Next steps are listening-based labels for the Judge and the generated-sound check, running the KSC model as the Reviewer, and publishing the in-house generation model.
